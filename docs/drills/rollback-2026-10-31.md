## Findings

1. **Rate limiter triggered during drill** — rapid repeated calls to `/v1/health/` during
   verification triggered the rate limiter (429). This is correct behaviour. In a real incident,
   monitoring pings the health endpoint at most once per minute so this will not occur.
   No action needed.

2. **`systemctl reload` vs `systemctl restart`** — `reload` (SIGHUP) does not fully reload
   Python module cache in all cases. A real broken deploy goes through the deploy script which
   runs `systemctl restart`, not `reload`. The drill used `restart` and confirmed full pick-up
   of code changes.

3. **`git checkout main -- <file>` is the fastest single-file rollback** for the self-hosted
   path. For a full deploy rollback (many files), use `git reset --hard <sha>` followed by
   `systemctl restart`.

## Rollback Command Reference (confirmed working)

```bash
# Single-file rollback (fastest for a known bad file)
git checkout main -- apps/api/views.py
sudo systemctl restart ff-consumer.service

# Full rollback to a specific commit
git reset --hard bd7d230
.venv/bin/pip install -q -r requirements/prod.txt --prefer-binary
sudo systemctl restart ff-consumer.service

# Verify
curl -s http://localhost:8001/v1/health/
```
