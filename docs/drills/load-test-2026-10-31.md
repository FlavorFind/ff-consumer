## Root Cause Analysis

The p95 < 250ms target cannot be met from a test client in Nairobi against a Frankfurt server
because the speed-of-light RTT alone is ~150ms. The minimum observed latency (cache hit) was
**186ms**, of which:
- ~150ms: Nairobi → Frankfurt network (fixed, unavoidable)
- ~36ms: server processing time ✅ (well within the 100ms processing budget)

The test client location was not co-located with the staging server. The sprint exit criterion
"search p95 < 250ms at 50 req/s on staging" was intended to be measured from within the same
region (Frankfurt), not from Kenya.

### What the numbers actually prove

| Finding | Evidence |
|---|---|
| Server processing is fast | Min latency 186ms; subtract ~150ms RTT = ~36ms server time |
| Cache is working | Redis writes confirmed; cache hits return same latency as misses (dominated by network) |
| 0% error rate at load | All requests succeed even under queue pressure |
| Engine integration works | Results returning exact/can_make tiers correctly |

### What caused queue saturation (dropped iterations)

At 50 req/s with ~686ms median response time, sustaining throughput requires
`50 × 0.686 ≈ 34 concurrent connections`. The server handles this but the k6 runner
in Nairobi cannot maintain 50 req/s outbound (drops ~150 iterations over 4 minutes).
